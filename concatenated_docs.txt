# VILR 2.0: Zero-Trust Agentic Payments

**AI agents can decide what to buy. They should not be allowed to decide whether money can move.**

VILR is a cryptographically verifiable, deterministic authorization gateway for agent-driven commerce. 

- **AI understands** (Semantic evaluation of intent)
- **Crypto verifies** (JCS + ECDSA P-256 signatures)
- **OPA authorizes** (Deterministic policy evaluation)
- **Redis protects execution** (Atomic two-phase idempotency)
- **Payment provider executes** (Mock/Razorpay endpoints)
- **Audit records evidence** (Tamper-evident hash chain)

## Problem & Why It Matters
Agents hallucinate. Merchants can be malicious. If an agent executes a payment directly, liability is undefined, and prompt injection can drain wallets.

## Core Insight
Split the intelligence from the authorization. Let AI negotiate, but enforce the transaction with cryptographic boundaries.

## 5. Baseline Comparison
VILR significantly outperformed Baseline A (unprotected agent), Baseline B (basic deterministic amount policy), and Baseline C (crypto validation only) by unifying Semantic Verification, Cryptographic integrity, and Execution Concurrency controls.

## 6. Known Weaknesses
- **LLM Non-determinism**: Even with temperature 0, semantic models can hallucinate. VILR mitigates this via strict OPA constraints.
- **Provider Timeouts**: Network failures between Gateway and Razorpay can still lead to `PAYMENT_UNKNOWN` states, which require async reconciliation.

## 7. Accepted Risks
- The `SemanticVerifier` is allowed to fail-open if the prompt matches the user intent conceptually but uses different vocabulary.
- Memory-based Audit Ledger is currently ephemeral. In production, this requires an append-only distributed database (e.g., QLDB).

# Interview Preparation (Judge Questions)

**Q1: What if the AI hallucinates a PASS?**
- 1-Sentence: OPA still strictly enforces the budget and allowed merchant list.
- 30-Second: The semantic assessment is merely untrusted evidence fed into OPA. If the AI returns 99.9% confidence for a $500 cart on a $100 budget limit, OPA statically denies it.
- Deep: `SemanticAssessment` is parsed as a typed object and injected into OPA Rego context. `allow == false` if `input.cart.total_amount > input.mandate.max_amount`, completely ignoring `input.semantic.status`.
- Evidence: `test_security_llm_cannot_override_budget`.

**Q2: Why not just use OAuth?**
- 1-Sentence: OAuth authorizes *who* the agent is, not *what* the transaction is.
- 30-Second: OAuth delegates scopes (e.g. `payment:write`). Once an agent has the token, it can execute *any* payment. VILR authorizes the specific payload cryptographically tied to the user intent.
- Deep: We separate Authenticity, Replay Protection, and Authorization. OAuth handles Authenticity but fails at intent-binding.
- Evidence: `architecture.md`.

**Q3: How do you prevent replay attacks?**
- 1-Sentence: Using a composite Redis key (`open_mandate_hash:checkout_hash`) and an atomic execution token.
- 30-Second: Before authorization, we `SETNX` a reservation key in Redis. If multiple identical requests hit the gateway, only one gets the reservation. The winner gets an execution token.
- Deep: Lua scripting handles atomic commit.
- Evidence: `test_concurrent_execution` hitting 100x requests.

**Q4: What if Redis goes down?**
- 1-Sentence: VILR fails closed. No reservation = no payment.
- 30-Second: If Redis is unavailable, the `try_reserve` throws a ConnectionError which is caught by the Gateway, returning a 503 HTTP Service Unavailable.
- Deep: Safe failure defaults to DENY.
- Evidence: `test_redis_unavailable` integration test.

# Technical Deep-Dive

**Cryptographic Binding:** Uses RFC 8785 JCS to canonically hash cart data, which is then signed via ES256 to create `checkout_hash`.
**Redis Reservation:** Employs a two-phase lock via `SETNX` (try_reserve) followed by Lua scripts for atomic `commit` (generating the execution token) and `release` upon failure.
**OPA Validation:** Restricts output to `AuthorizationDecision`. It never calls external APIs, ensuring sub-10ms evaluation times.
**Audit Hash Chain:** Uses SHA-256 hashing to link the previous transaction hash with the current transaction state, creating a localized immutable ledger.
**PAYMENT_UNKNOWN Handling:** Transitions to a non-terminal unknown state without retries, requiring a reconciliation polling worker to finalize safely.
